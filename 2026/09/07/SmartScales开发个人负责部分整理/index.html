SmartScales 开发个人负责部分整理

项目：宠境智护（SmartScales）—— 基于 YOLO 视觉模型 + 环境规则评估 + LLM 文案生成的宠物健康诊断系统

三轮工作从“可追溯”逐步扩展到“可治理、可协作”：第一轮做诊断结果的持久化与失败恢复；第二轮做图片资源的统一治理；第三轮补齐后台媒体治理与反馈处理闭环

一、第一轮：诊断评估快照与重试接口

1.1 任务范围

补全 diagnosis_tasks 表的 7 个快照字段 + 实现历史读取走快照逻辑 + 新增重试接口

边界说明：YOLO 模型识别、环境规则评估、LLM 文案生成是别的同学的模块，本轮做的是”在他们产出结果后，把版本 + 结果固化进表，并在失败时提供受限重试”

1.2 技术难点

难点1：为什么需要快照——模型/规则会迭代

这是个”互联网+”宠物健康诊断项目，YOLO 视觉模型会持续训练迭代（v1.0 → v1.1 识别率提升），环境评估规则会调优（温度阈值从 30℃ 改成 28℃），LLM 提示词会优化

这些迭代对”新诊断”是好事，但对”历史报告”是灾难：

在涉及宠物健康决策的系统中，这类“历史结论漂移”会削弱用户对报告的信任。解法是快照固化：

本质：这是写时复制（Copy-on-Write）思想在业务层的应用——诊断提交的瞬间，把”依赖的外部服务版本 + 结果”冻结一份，后续外部服务怎么变，历史报告展示不受影响

难点2：七个字段各自解决什么问题

字段 当前状态 解决的问题
yolo_model_version 已写入 知道当时用哪个模型，便于判断旧结论是否还可信
rule_version 已写入 知道当时用哪版规则，规则改了旧结论的判定依据不丢
yolo_result_snapshot 已写入 结构化检测结果快照，含类别、置信度、边界框；重试时复用视觉证据，避免再次调 YOLO
llm_status 已写入 SUCCESS / FALLBACK / FAILED 三态，决定能否重试
image_asset_ids 已写入 MinIO 稳定 objectKey，URL 过期后图片仍能恢复
parent_assessment_id 已建模、未写入 为后续”从某次评估发起复查”预留源记录关联
recheck_of 已建模、未写入 为后续复查关系查询预留关联字段

难点3：MinioUtil 改造——从 URL 到 objectKey

第一轮为了支持 image_asset_ids 存 objectKey，改了 MinioUtil 的上传方法：

从”只给临时 URL”到”同时给稳定标识 + 临时 URL”。诊断快照存 objectKey，展示时再换 URL——为第二轮的统一媒体服务埋了伏笔

难点4：重试接口的状态机

重试时复用什么、重新跑什么：

  • ✅ 复用：原始输入、YOLO 快照（不重新调 YOLO）、objectKey（重新生成预签名 URL）
  • ❌ 重新跑：环境规则评估、LLM（基于当时实现重新构建上下文并再次调用）

为什么 SUCCESS 拒绝重试：

  • 数据一致性：SUCCESS 状态下重试会覆盖已有结论，用户看到的报告可能前后不一致
  • 资源保护：每次重试都要调 LLM（API 计费）+ 重新跑环境规则，SUCCESS 重试是无意义消耗

重试是”失败修复流程”，不是严格意义上的不可变审计版本。如果要做到严格审计级复现，还需要再固化规则参数快照、Prompt/知识库版本、LLM 模型版本和完整推理上下文

1.3 设计边界与现状

这套设计保证了历史报告结论稳定——历史详情直接读取已固化的 result 报告 JSON 和版本号，不会在查询时重新调用 YOLO、规则或 LLM，不因后续模型或规则升级而漂移。

但“报告结论稳定”不等于“历史图片访问已经完全稳定”：诊断任务目前同时保存旧的预签名 URL（image_urls）和稳定 objectKey（image_asset_ids），普通历史详情仍直接返回已保存的 URL；只有重试流程会根据 objectKey 重新生成 URL。因此，旧 URL 过期后，诊断历史详情页暂不会自动恢复图片，仍需要将普通读取链路改为基于 objectKey 换链。

但它不是严格审计级的”完全可复现”：

  • 没有固化物种环境标准当时的具体数值
  • 没有固化 Qwen 模型版本、Prompt 版本、知识库版本
  • 重试时会重新执行环境规则和 LLM（不复刻当时的 Prompt 和模型版本）

复查关联字段（parent_assessment_id / recheck_of）已完成数据库迁移、实体映射和响应 DTO 透传，但当前仓库中没有业务代码写入它们，也没有”发起复查”入口或按父记录查询的接口——这是为后续功能预留的数据模型

1.4 面试加分：主动说出的优化方向

如果对方问”还有什么可优化”，主动答这四点：

  1. 严格审计复现：当前版本固化了最终结果和核心视觉证据；若要做到严格可审计复现，需再固化规则参数快照、Prompt/知识库版本、LLM 模型版本和完整推理上下文
  2. 重试的规则版本漂移：当前重试复用 YOLO 快照，但会重新执行环境规则；后续可以把完整规则评估结果也存为快照，或让重试显式选择”沿用旧规则”还是”使用新规则”

二、第二轮：统一 MinIO 媒体服务

2.1 任务范围

将主要的上传、访问和删除能力收敛到 MediaService，统一 objectKey 命名和安全校验，并接入异常观察图片附件

边界说明：MinIO 服务和 bucket 是前人搭好的；宠物资料没有单独的 MultipartFile 上传逻辑，它是前端先走 /api/upload/image 再把 URL 放进宠物资料 JSON；当前仍有少量业务服务直接依赖 MinioUtil 做 objectKey → 预签名 URL 的转换（DiagnosisService 的 regenerateImageUrls、AbnormalObservationService 的 regenerateUrl），这些读取侧调用绕过了 MediaService 的归属校验。其中异常观察的 Controller/Service 目前只校验宠物或记录是否存在，未把当前登录用户传入做归属校验；若用户能触达他人 petId，可能读取他人记录并换出图片 URL。该问题应列为高优先级安全待办：业务记录查询先校验用户归属，媒体 URL 解析统一收口到带 userId 校验的 MediaService。

2.2 技术难点

难点1：收敛前的散落现状

问题：校验规则各写各的（有的查扩展名有的不查）、objectKey 命名混乱（有的 images/uuid 有的 diagnosis/userId/uuid）、改一处要找五处

难点2：MediaService 统一入口——四个方法的设计

设计要点：

  • scene 参数统一 objectKey 命名：scene/userId/uuid.ext，第一段是业务场景，第二段是归属用户
  • 单文件和批量上传复用底层的 validate(file) 与 doUpload(...)，批量接口把用户和场景校验提到循环外执行，避免重复校验
  • 返回 MediaObjectInfo DTO 含 objectKey + url + mime + size + 原始文件名 + 上传时间，调用方各取所需
  • 批量上传用 CompletableFuture.supplyAsync 并发提交任务，最后按原始顺序逐个 join() 汇总结果

难点3：安全校验——输入校验与授权校验两层分离

媒体服务分为输入校验和授权校验两层，职责分离：

第一层：上传前的输入校验（每个文件都要过）

第二层：访问与删除时的授权校验（防水平越权）

两层分离的好处：输入校验保证上传内容合法，授权校验保证用户只能访问/删除自己的资源

各关卡解决的具体威胁：

关卡 威胁 说明
内容非空 空文件占满 inode 防恶意提交空文件
10MB 上限 资源耗尽 防大文件撑爆磁盘/带宽
扩展名白名单 明显不符合约定的文件 仅从原始文件名提取扩展名，evil.php 改名 evil.jpg 能通过——MinIO 对象存储不执行 PHP 风险较低，但不是完整的内容安全校验
scene 正则 路径穿越 scene=../../etc → objectKey 逃出 bucket 合法目录；必须小写字母开头，防 . .. / 等字符
归属校验 水平越权 用户 A 拿 token 去删用户 B 的图——RBAC 管”能不能删”，归属校验管”能删谁的”

面试加分：扩展名白名单不是完整的文件内容安全校验——要进一步防范伪装图片，应补充 MIME 嗅探、图片解码校验，必要时进行转码或病毒扫描

scene 正则 [a-z][a-z0-9-_]{0,31} 的设计细节：

  • 必须小写字母开头（防 . .. / 等路径穿越字符）
  • 只允许小写字母、数字、连字符、下划线
  • 最长 32 字符（防超长名打爆文件系统）
  • 先 normalizeScene 转小写再校验（AbNormal → abnormal），用户体验好但不放宽安全边界

难点4：objectKey 归属校验——基于资源所有者的访问控制

比 RBAC（角色权限）更细粒度：RBAC 管”你能不能删图片”，归属校验管”你能删谁的图片”。用户 A 有删除权限，但只能删自己的

难点5：objectKey 入库 + URL 动态生成——存用分离

两种业务的实现差异：

业务 入库存什么 读取时怎么换 URL 是否过归属校验
异常观察（第二轮新建） objectKey（image_urls 列存 key） 读取时逐个调 minioUtil.getPresignedUrl 换链 ❌ 绕过 MediaService，直接调 MinioUtil
诊断（第一轮已有） URL + objectKey 都存（imageUrls 存 URL，imageAssetIds 存 key） 普通读取直接用存死的 URL；重试时才从 imageAssetIds 换链。旧 URL 过期后普通详情不能自动恢复 ❌ 同样绕过 MediaService

现状：异常观察是真正的存用分离（只存 objectKey），诊断模块则保留了 URL + objectKey 双份。两者的读取侧换链都直接调 MinioUtil，没走 MediaService 的 requireOwned 归属校验——后续应收口为统一 URL 解析能力

为什么不直接存 URL：

  • 预签名 URL 7 天过期；保存 objectKey 后可由后端重新生成 URL，但当前诊断普通详情尚未接入这一步
  • 换 MinIO 服务器 → 所有 URL 失效，数据库得批量改
  • URL 泄露 → 7 天内任何人能看（预签名无鉴权）

API 层的设计（避免 image_urls 这个历史命名的语义混淆）：

  • 写入接口用 imageKeys（语义明确：稳定 objectKey）
  • 读取响应同时返回 imageKeys 和 imageUrls：前者用于编辑回填和持久化，后者用于界面展示

难点6：幂等删除

幂等的本质：重复执行不出错、终态一致。不是”每次返回 true”，是”多次调用和一次调用的效果一样”。删两次和删一次，最终状态都是”文件不存在”，这就叫幂等

难点7：UploadController 委托——门面模式保兼容

老接口 /api/upload/image 内部委托 MediaService，对外返回值不变（URL 字符串）。头像、宠物照片等既有调用方零感知，不用改一行代码

这是门面模式的典型应用：新系统在后面跑，老接口在前面兜着，渐进迁移

难点8：异常观察图片附件——前后端协作设计

后端：

  • 数据库列 image_urls 存逗号分隔的 objectKey（历史命名，实际是 key 不是 URL）
  • 写入接口接收 imageKeys，读取响应同时返回 imageKeys 和动态生成的 imageUrls

2.3 面试加分：主动说出的优化方向

当前安全待办：读取侧的 objectKey → 预签名 URL 转换尚未统一走 MediaService 的 requireOwned 校验；异常观察接口也尚未将当前用户传入服务层校验 petId/记录归属。应先完成业务数据所有权校验，再收口为带 userId 的统一 URL 解析能力。

  1. 文件内容安全：目前是扩展名白名单，可加 MIME 嗅探、图片解码、转码和异步病毒扫描，避免伪装文件
  2. 异步批处理的资源控制：当前 CompletableFuture.supplyAsync 使用默认公共线程池；生产环境应使用受控的 TaskExecutor，限制并发量、隔离存储 IO，并实现部分失败补偿/清理孤儿对象
  3. 读取侧收口与安全加固：当前 DiagnosisService（regenerateImageUrls）和 AbnormalObservationService（regenerateUrl）里的 objectKey → 预签名 URL 转换是直接调 MinioUtil，绕过了 MediaService 的 requireOwned 归属校验——只要能触达对应业务接口即可换出 URL。后续应收口为 MediaService 的统一 URL 解析能力，让读取侧也走 userId 归属校验

2.4 V3.0 Sprint 交付范围与未完成接入

本轮已完成统一媒体能力，以及诊断、异常观察两个真实接入场景；头像和宠物照片通过旧接口兼容接入。按照 V3.0 Sprint 文档，问题反馈附件、社区帖子图片、商品图片也应接入同一媒体能力，目前仍由对应业务模块继续完成，不能表述为“所有业务场景均已统一”。

三、第三轮：后台媒体与反馈处理闭环

3.1 任务范围

本轮对应 V4.1 后台媒体与反馈后台任务，主要交付两组管理端 API：

  • 后台媒体：管理员上传图片、按 objectKey 重新生成预签名 URL、删除未被业务引用的对象
  • 反馈后台：分页筛选、详情查询、内部备注、受控状态流转、并发版本冲突和状态审计
  • 后台权限：复用现有登录 Token，根据 users.role 对 /api/admin/** 做服务端管理员校验
  • 数据库迁移：为 users 增加 role、为 feedback 增加 version，新建内部备注表和状态审计表

边界说明：本轮交付的是可供统一后台页面直接联调的后端接口，不新建第二套 admin-web；统一后台登录接口和后台前端基座属于团队其他任务。本轮暂时复用现有登录态，在每个后台入口继续做角色校验。

3.2 技术难点

难点1：后台权限不能只靠“前端隐藏按钮”

如果只在前端根据角色隐藏菜单，普通用户仍然可以绕过页面，直接用 Postman 或 curl 调后台接口。因此本轮把认证与授权拆成两层：

这里要区分两个概念：

  • 认证（Authentication）：你是谁？没有有效 Token 返回 401
  • 授权（Authorization）：你能不能做这个操作？已登录但不是管理员返回 403

users.role 是权限判断的唯一事实来源，默认值为 USER。即使前端参数伪造角色，后端仍以数据库为准。

难点4：反馈处理不是任意改状态，而是显式状态机

后台处理反馈只允许以下路径：

  • PENDING → PROCESSING：管理员接单并开始处理
  • PROCESSING → RESOLVED：问题处理完成
  • RESOLVED → PROCESSING：用户复现或问题重新出现
  • 其他跳转：返回 422

为什么不允许 PENDING → RESOLVED？因为它跳过了“谁开始处理、何时处理”的过程状态，不利于团队协作和审计。为什么允许重新打开？因为“已解决”不是不可逆终态，真实客服场景中问题可能复发。

难点5：乐观锁防止多管理员互相覆盖

场景：管理员 A 和 B 同时打开反馈详情，都看到 version=1。A 先把状态改成 PROCESSING；B 的页面没刷新，又提交 RESOLVED。如果只按 id 更新，B 会静默覆盖 A 的处理结果。

本轮的更新 SQL 同时匹配 id 和客户端版本：

判断逻辑：

服务层在执行 SQL 前会先比较一次版本，用于尽早返回友好错误；真正防止“比较后、更新前又被别人抢先修改”的，是 SQL 的 WHERE version = ? 条件。

为什么不用 synchronized：

  • synchronized 只保护单个 JVM，服务多实例部署后失效
  • 数据库条件更新天然跨实例生效
  • 反馈冲突概率低，乐观锁不需要长期占有数据库行锁

新增内部备注也会把 version 加一，因为备注属于详情上下文的一部分。其他管理员基于旧详情继续操作时应先刷新，避免忽略最新处理信息。

难点6：内部备注与状态审计分表

两种记录看起来都像“管理员写了一段话”，但职责不同：

数据 用途 是否跟随状态变化 普通用户是否可见
feedback_internal_note 管理员协作、排查记录 不要求改变状态 否
feedback_status_audit 记录 from/to、操作人、原因、时间 每次成功流转都写 否

状态更新和审计写入放在同一个事务中：状态改成功但审计失败时整体回滚，避免出现“状态变了却没有操作记录”的半成功状态。

当前后台详情返回内部备注，但还没有提供状态审计列表接口；审计数据已经完整落库，可在后续管理页面增加时间线展示。

难点7：数据库迁移与本地可验收环境

本轮迁移新增：

同时修复了全量初始化脚本的 MySQL 8.4 兼容问题：移除不兼容的 ADD COLUMN IF NOT EXISTS、移除存在外键引用时不安全的 TRUNCATE product、移除依赖不存在用户的演示通知数据。

配置层把数据库和 MinIO 凭据改为环境变量，避免继续把真实密码提交到仓库。本地 MySQL 只监听 127.0.0.1；MinIO 也只绑定本机端口用于接口验收。

3.4 设计边界与优化方向

  1. 引用扫描是显式清单：新增业务表或媒体字段时，必须同步更新 MediaReferenceService，否则保护范围不会自动扩展。长期可以引入统一媒体资产表和引用关系表。
  2. 逗号分隔字段限制查询能力：当前使用 FIND_IN_SET 兼容历史字段，数据量大后索引难以生效。更规范的做法是媒体附件关联表，一行表示一条业务引用。
  3. 角色模型仍较粗：目前只有 USER / ADMIN / SUPER_ADMIN，后续可拆成媒体管理、反馈处理、商品管理等细粒度权限，并统一接入 Spring Security。
  4. 每次请求都会查询角色：实时性高，但增加数据库访问；可以在保证角色变更及时失效的前提下做短时缓存。
  5. 审计暂未对外查询：状态审计已落库，但后台详情只返回内部备注；后续可增加审计时间线接口。
  6. 后台页面尚未接入：本轮完成 API 和数据库闭环，仍需团队统一 admin-web 和后台登录基座完成页面联调。
  7. MinIO 仅作为本地验收环境：社区版已经归档且不再提供预编译二进制，当前本机构建适合开发验收；生产部署应评估持续维护和商业支持方案。

四、面试高频追问（更新版）

问题 回答要点
当前诊断历史图片会自动换链吗？ 不会。普通详情当前直接返回已保存的预签名 URL；只有重试按 image_asset_ids 重新生成 URL。应将普通读取链路改为基于 objectKey 的受权换链。
快照和日志的区别？ 日志记过程（调了什么、返回什么），快照存结论（最终报告 JSON + 依赖版本 + 视觉证据）。看历史报告读快照不重跑；重试是失败修复流程，不是严格不可变版本
历史报告真的不重跑吗？ 普通历史详情查询只查数据库，不重新调 YOLO/规则/LLM。但重试接口会重新跑规则和 LLM（不复刻当时的 Prompt 和模型版本），复用 YOLO 快照和 objectKey；当前普通详情的图片 URL 过期后尚未自动按 objectKey 换链
为什么不实时重新跑模型？ 模型迭代会导致结论漂移；GPU 推理成本高；LLM 按次计费。快照固化后零成本读取。但当前设计不是严格审计级复现——没固化规则参数、Prompt/知识库版本、LLM 版本
objectKey 为什么不直接存 URL？ 预签名 URL 会过期，服务地址变化时也难迁移，泄露后在有效期内可被访问。objectKey 是稳定引用，可由后端按需生成新 URL；当前诊断普通详情还需补上自动换链
扩展名白名单防得了伪装吗？ 只能阻止明显不符合约定的文件（无扩展名、奇怪扩展名）。evil.php 改名 evil.jpg 能通过。MinIO 对象存储不执行 PHP 风险较低，但不是完整内容安全——后续可加 MIME 嗅探、图片解码校验
归属校验为什么不用 RBAC？ RBAC 管”能不能删”，管不了”删谁的”。用户有删除权限但只能删自己的，这是所有权校验，比角色更细粒度
scene 正则为什么必须小写字母开头？ 防 . .. / 等路径穿越字符。scene 能是 ../../etc 就逃出 bucket 了
幂等删除为什么第二次返回 false？ 幂等的定义是”重复执行终态一致”，不是”每次返回 true”。删两次和删一次效果一样（文件不存在），就是幂等
老接口为什么不直接删？ 头像、宠物照片等调用方还在用。门面模式保兼容，内部委托新服务，对外零感知
SUCCESS 为什么拒绝重试？ 防止已成功生成的报告被覆盖，避免用户看到同一任务的结论前后变化；同时避免无意义消耗 LLM 资源
批量上传怎么实现的？ 先同步校验全部文件，再用 CompletableFuture.supplyAsync 并发上传，最后按原始顺序逐个 join 汇总结果。不是 allOf 统一等待，后续可改成 allOf + 集中异常处理
预签名 URL 为什么 7 天？ 当前实现固定为 7 天，用于兼顾可用性与暴露窗口；尚未配置化，也没有独立的产品规则将其定义为“复诊周期”
parent_assessment_id / recheck_of 实现了吗？ 已完成数据库迁移、实体映射和响应透传，但当前仓库没有业务代码写入它们，也没有”发起复查”入口。这是为后续功能预留的数据模型
数据库列名为什么是 image_urls 但存的是 objectKey？ 异常观察是真正的存用分离（只存 objectKey）；诊断模块则保留了 URL + objectKey 双份，普通读取直接用存死的 URL，重试时才从 imageAssetIds 换链。API 层为避免语义混淆，写入用 imageKeys，读取同时返回 imageKeys 和动态生成的 imageUrls
读取侧换链走了归属校验吗？ ❌ 没走。DiagnosisService 的 regenerateImageUrls 和 AbnormalObservationService 的 regenerateUrl 都直接调 MinioUtil，绕过了 MediaService 的 requireOwned；异常观察接口还需补充 petId/记录的用户归属校验。后续应收口为统一 URL 解析能力
后台菜单只让管理员看见，为什么还要后端鉴权？ 前端隐藏只改善界面，不能阻止用户直接构造 HTTP 请求。后台接口必须根据服务端登录态和数据库角色做授权，未登录返回 401，已登录但无权限返回 403。
为什么后台上传又增加魔数识别？ 扩展名和请求 MIME 都由客户端提供，可以伪造。魔数来自文件真实字节；再与扩展名交叉校验，才能拒绝文本改名 PNG、PNG 改名 JPG 等伪装。
乐观锁为什么既在 Java 比版本，又在 SQL 里带 version？ Java 预检用于尽早给出友好错误；真正消除竞态的是 WHERE id = ? AND version = ? 的条件更新。否则两次请求都通过 Java 检查后仍可能互相覆盖。
为什么不用 synchronized 解决管理员并发？ synchronized 只对单 JVM 有效，多实例部署后无法互斥。数据库条件更新跨实例生效，而且反馈冲突频率低，乐观锁比长期持有悲观锁更合适。
添加内部备注为什么也要 version + 1？ 备注会改变反馈详情的协作上下文。版本递增能让其他管理员知道页面已经过期，避免忽略刚新增的排查结论继续提交状态。
状态审计和内部备注为什么分表？ 备注是自由协作信息；审计必须结构化记录 from/to、操作人、原因和时间。两者生命周期和查询用途不同，分表能保证审计语义稳定。
媒体为什么不能直接删除？ objectKey 可能被商品、订单快照、社区、诊断等业务引用。删除前先扫描引用，存在引用返回 409；请求合法，但资源当前状态与删除操作冲突。

五、设计模式与架构思想总结

模式/思想 落地场景
写时复制（Copy-on-Write） 诊断快照：提交瞬间冻结依赖版本 + 结果，防止历史漂移
门面模式（Facade） UploadController 委托 MediaService，老接口保兼容
纵深防御（Defense in Depth） 输入校验（空/大小/类型/scene/认证）+ 授权校验（归属），两层分离
基于所有者的访问控制 objectKey 第二段 userId 与认证用户比对，防水平越权
RBAC 后台接口根据 users.role 判断 ADMIN / SUPER_ADMIN，不能依赖前端隐藏菜单
存用分离 objectKey 入库（永久）+ URL 动态生成（临时）
状态机守卫 诊断重试的 FAILED/FALLBACK/SUCCESS 判断；反馈的 PENDING/PROCESSING/RESOLVED 流转约束
乐观并发控制 feedback.version + 条件更新，防止多管理员静默覆盖
事务一致性 反馈状态更新和状态审计同事务提交，避免半成功
引用完整性保护 删除媒体前扫描业务引用，存在引用返回 409
幂等设计 删除接口重复调用终态一致

六、一句话总结

交付边界：以上总结的是三轮已经完成的后端能力，不代表所有前后台场景均已闭环；当前仍需补齐普通诊断详情按 objectKey 换链、读取侧归属校验、统一媒体引用模型，以及团队 admin-web 和后台登录基座的页面联调。

第一轮做诊断结果的持久化与失败恢复：诊断提交时把最终报告、YOLO 模型版本、规则版本、结构化 YOLO 检测结果、LLM 执行状态和 MinIO objectKey 固化到 diagnosis_tasks。历史详情直接读取已落库的报告结果，不会在查询时重新调用模型、规则或 LLM，从而避免历史展示随服务升级而漂移。对于 LLM 的失败或降级结果，增加了带用户归属和状态守卫的重试入口：复用历史输入、YOLO 快照和 objectKey，重新生成临时图片 URL 后重试 LLM；成功记录不允许重试，避免覆盖用户已确认的结论。复查关联字段已经完成建模和透传，为后续”发起复查”功能预留。

第二轮做图片资源的统一治理：将主要的上传、访问和删除能力收敛到 MediaService，统一 objectKey 命名、文件大小和扩展名校验、场景名约束、认证用户校验及对象归属校验。业务表持久化 objectKey，展示时动态换取 7 天有效的预签名 URL；这样 URL 过期不影响历史资源引用。旧的上传接口保留原返回格式并委托新服务，避免头像和宠物照片等现有调用方改造。最后，把该能力完整接入异常观察：前端支持最多 9 张图片的选择、预览和编辑回填，后端存 objectKey、读时生成展示 URL

第三轮做后台媒体与反馈处理闭环：后台接口复用现有登录态并根据数据库角色做服务端授权；媒体上传增加 JPEG/PNG/WebP 魔数识别和扩展名一致性校验，删除前扫描商品、订单、社区、诊断等业务引用。反馈后台支持分页筛选、详情、内部备注和受控状态流转，通过 version 条件更新解决多管理员并发覆盖，并在同一事务中记录状态审计。自动化测试 73 项全部通过，端到端验证了 403 权限隔离、409 版本冲突、图片哈希一致性、伪装文件拒绝和对象真实删除。

七、术语备注

术语 通俗解释 本项目中的例子
读取侧 查询、展示数据的一端 用户打开历史诊断报告或异常观察记录
写入侧 提交、保存数据的一端 用户上传图片并提交诊断或异常观察记录
换链 根据稳定文件标识重新生成访问链接 用 objectKey 重新换取 MinIO 预签名 URL
自动换链 用户读取历史记录时，系统自动生成新链接 诊断普通详情尚未完成这一能力；当前只有重试时会换链
归属校验 校验资源是否属于当前登录用户 比较 objectKey 中的 userId 与 token 中的用户 ID
水平越权 用户通过猜测 ID 等方式访问其他普通用户的数据 用户 A 不应通过 petId 访问用户 B 的异常观察和图片
预签名 URL 可直接访问私有对象、但有有效期的临时链接 MinIO 当前生成的图片 URL 有效期为 7 天
objectKey 对象存储中文件的稳定唯一标识 abnormal/13/uuid.jpg，不会因 URL 过期而变化
历史结论漂移 规则或模型更新后，旧数据重新计算得出不同结论 YOLO 或环境阈值升级后，旧报告不应被重新计算改写
快照 在提交时冻结当时的关键数据和结果 保存模型版本、规则版本、YOLO 结果和 LLM 状态
存用分离 数据库存稳定标识，展示时再生成临时访问地址 异常观察表存 objectKey，读取时再换 URL
状态机守卫 按当前状态限制可执行的操作 只有 FAILED 或 FALLBACK 诊断允许重试
RBAC 根据用户角色决定能否执行一类操作 只有 ADMIN / SUPER_ADMIN 能访问后台接口
乐观锁 不先锁住数据，提交时检查版本是否仍一致 更新反馈时同时匹配 id 和 version，旧版本返回 409
条件更新 只有 WHERE 条件仍满足时才执行更新 WHERE id = ? AND version = ? 防止并发覆盖
状态审计 结构化记录状态从哪里变到哪里、由谁操作、为什么 feedback_status_audit 保存 from/to、管理员、原因和时间
内部备注 仅供后台协作使用、不展示给普通用户的说明 管理员记录复现过程、日志补充和处理结论
魔数 文件开头用于识别真实格式的固定字节特征 PNG 以 89 50 4E 47 0D 0A 1A 0A 开头
业务引用保护 删除共享资源前检查是否仍被业务数据使用 商品或诊断仍引用 objectKey 时拒绝删除并返回 409
幂等 同一操作重复执行，最终状态保持一致 同一文件重复删除后，最终都处于“不存在”状态
门面模式 保留旧入口，内部委托新实现 旧 /api/upload/image 接口内部委托 MediaService
向后兼容 系统升级后，旧页面和旧调用仍可用 头像、宠物照片页面无需立刻改造上传接口
降级 外部能力失败时返回可用的基础结果 LLM 失败时使用规则结果生成回退报告
孤儿文件 已上传但未被任何业务记录引用的文件 图片上传成功、异常观察记录保存失败后留下的 MinIO 对象
