SmartScales 两轮开发核心知识点

项目：宠境智护（SmartScales）—— 基于 YOLO 视觉模型 + 环境规则评估 + LLM 文案生成的宠物健康诊断系统

两轮工作围绕”可追溯”展开：第一轮做诊断结论的快照固化，保证历史报告不可变；第二轮做媒体资源的统一治理，保证图片存得安全、找得到、删得对

一、第一轮：诊断评估快照与重试接口

1.1 任务范围

补全 diagnosis_tasks 表的 7 个快照字段 + 实现历史读取走快照逻辑 + 新增重试接口

边界说明：YOLO 模型识别、环境规则评估、LLM 文案生成是别的同学的模块，本轮做的是”在他们产出结果后，把版本 + 结果固化进表，并保证历史读取不重新调他们的服务”

1.2 技术难点

难点1：为什么需要快照——模型/规则会迭代

这是个”互联网+”宠物健康诊断项目，YOLO 视觉模型会持续训练迭代（v1.0 → v1.1 识别率提升），环境评估规则会调优（温度阈值从 30℃ 改成 28℃），LLM 提示词会优化

这些迭代对”新诊断”是好事，但对”历史报告”是灾难：

医疗类系统里这种”历史结论漂移”是红线，解法是快照固化：

本质：这是写时复制（Copy-on-Write）思想在业务层的应用——诊断提交的瞬间，把”依赖的外部服务版本 + 结果”冻结一份，后续外部服务怎么变，历史报告不受影响

难点2：七个字段各自解决什么问题

字段 解决的问题 不存的后果
yolo_model_version 知道当时用哪个模型 无法判断旧结论是否还可信
rule_version 知道当时用哪版规则 规则改了，旧结论的判定依据丢失
yolo_result_snapshot YOLO 原始检测框 JSON 想复现当时的可视化，得重新跑模型
llm_status LLM 是否成功 SUCCESS/FALLBACK/FAILED 三态决定能否重试
image_asset_ids 图片的稳定引用 URL 过期后历史报告的图全成死链
parent_assessment_id 复查链 不知道这次诊断是基于哪次来的
recheck_of 被复查记录 复查关系无法追溯

难点3：MinioUtil 改造——从 URL 到 objectKey

第一轮为了支持 image_asset_ids 存 objectKey，改了 MinioUtil 的上传方法：

从”只给临时 URL”到”同时给稳定标识 + 临时 URL”。诊断快照存 objectKey，展示时再换 URL——为第二轮的统一媒体服务埋了伏笔

难点4：重试接口的状态机

为什么 SUCCESS 拒绝重试，面试追问的回答层次：

  • 数据一致性：SUCCESS 状态下重试会覆盖已有结论，用户看到的报告可能前后不一致
  • 幂等性：重试接口应该幂等——同样的请求执行一次和多次结果一致。SUCCESS 允许重试 → 同一个任务多次重试可能产出不同结论 → 破坏幂等
  • 资源保护：每次重试都要调 YOLO（GPU 推理）+ LLM（API 计费），SUCCESS 重试是浪费资源

1.3 创新点

  • 快照 + objectKey 双固化：版本号 + 结果 JSON + 稳定图片引用，三者一起保证历史报告完全可复现，不依赖任何外部服务的当前状态
  • 重试状态机守卫：不是”能不能重试”的问题，是”该不该重试”的问题——SUCCESS 拒绝是业务规则，不是技术限制

二、第二轮：统一 MinIO 媒体服务

2.1 任务范围

收敛全项目散落的图片上传逻辑为统一服务 + 接入异常观察图片附件

边界说明：MinIO 服务和 bucket 是前人搭好的，本轮做的是把散落调用收口 + 补安全校验 + 接新业务

2.2 技术难点

难点1：收敛前的散落现状

问题：校验规则各写各的（有的查扩展名有的不查）、objectKey 命名混乱（有的 images/uuid 有的 diagnosis/userId/uuid）、改一处要找五处

难点2：MediaService 统一入口——四个方法的设计

设计要点：

  • scene 参数统一 objectKey 命名：scene/userId/uuid.ext，第一段是业务场景，第二段是归属用户
  • uploadBatch 复用 upload 的校验逻辑，不是再写一遍——每个文件都过一遍 validate()
  • 返回 MediaObjectInfo DTO 含 objectKey + url + mime + size + 原始文件名 + 上传时间，调用方各取所需

难点3：安全校验链（纵深防御，五道关卡）

每道关卡解决的具体威胁：

关卡 威胁 攻击场景
内容非空 空文件攻击 上传空文件占满 inode
大小限制 资源耗尽 上传 2GB 文件撑爆磁盘/带宽
扩展名白名单 文件类型伪装 evil.php 改名 evil.jpg 上传后执行
scene 正则 路径穿越 scene=../../etc → objectKey 跑出 bucket 合法目录
归属校验 越权删除 用户 A 拿 token 去删用户 B 的图

scene 正则 [a-z][a-z0-9-_]{0,31} 的设计细节：

  • 必须小写字母开头（防 . .. / 等路径穿越字符）
  • 只允许小写字母、数字、连字符、下划线
  • 最长 32 字符（防超长名打爆文件系统）
  • 先 normalizeScene 转小写再校验（AbNormal → abnormal），用户体验好但不放宽安全边界

难点4：objectKey 归属校验——基于资源所有者的访问控制

比 RBAC（角色权限）更细粒度：RBAC 管”你能不能删图片”，归属校验管”你能删谁的图片”。用户 A 有删除权限，但只能删自己的

难点5：objectKey 入库 + URL 动态生成——存用分离

为什么不直接存 URL：

  • URL 7 天过期 → 历史报告的图全成死链
  • 换 MinIO 服务器 → 所有 URL 失效，数据库得批量改
  • URL 泄露 → 7 天内任何人能看（预签名无鉴权）

难点6：幂等删除

幂等的本质：重复执行不出错、终态一致。不是”每次返回 true”，是”多次调用和一次调用的效果一样”。删两次和删一次，最终状态都是”文件不存在”，这就叫幂等

难点7：UploadController 委托——门面模式保兼容

老接口 /api/upload/image 内部委托 MediaService，对外返回值不变（URL 字符串）。头像、宠物照片等既有调用方零感知，不用改一行代码

这是门面模式的典型应用：新系统在后面跑，老接口在前面兜着，渐进迁移

难点8：异常观察图片附件——前端交互设计

三、面试高频追问

问题 回答要点
快照和日志的区别？ 日志记过程（调了什么、返回什么），快照存结论（最终判定结果 + 依赖版本）。日志保证可追溯，快照保证不可变。看历史报告读快照不看日志
为什么不实时重新跑模型？ 模型会迭代，重跑可能结论漂移；GPU 推理成本高；LLM 按次计费。快照固化后零成本读取
objectKey 为什么不直接存 URL？ URL 7 天过期 → 死链；换服务器 → 批量改库；URL 泄露 → 7 天裸奔。objectKey 永不变，URL 随时换
归属校验为什么不用 RBAC？ RBAC 管”能不能删”，管不了”删谁的”。用户有删除权限但只能删自己的，这是所有权校验，比角色更细粒度
scene 正则为什么必须小写字母开头？ 防 . .. / 等路径穿越字符。如果 scene 能是 ../../etc，objectKey 就可能逃出 bucket
幂等删除为什么第二次返回 false？ 幂等的定义是”重复执行终态一致”，不是”每次返回 true”。删两次和删一次效果一样（文件不存在），就是幂等
老接口为什么不直接删？ 头像、宠物照片等调用方还在用。门面模式保兼容，内部委托新服务，对外零感知，渐进迁移
SUCCESS 为什么拒绝重试？ 数据一致性（覆盖已有结论）+ 幂等性（重试破坏幂等）+ 资源保护（GPU/LLM 成本）
批量上传怎么实现的？ uploadBatch 内部 CompletableFuture allOf 等待全部完成，每个文件复用 upload 的校验逻辑
预签名 URL 为什么 7 天？ 兼顾可用性与安全性：太短用户刷新就看不到图，太长泄露了风险大；业务场景是诊断报告，7 天覆盖一个复诊周期

四、设计模式与架构思想总结

模式/思想 落地场景
写时复制（Copy-on-Write） 诊断快照：提交瞬间冻结依赖版本 + 结果
门面模式（Facade） UploadController 委托 MediaService，老接口保兼容
纵深防御（Defense in Depth） 五道安全校验关卡，层层拦截
基于所有者的访问控制 objectKey 第二段 userId 与登录用户比对
存用分离 objectKey 入库（永久）+ URL 动态生成（临时）
状态机守卫 重试接口的 FAILED/FALLBACK/SUCCESS 三态判断
幂等设计 删除接口重复调用终态一致

五、一句话总结

第一轮做”历史不可变”：诊断提交时冻结模型版本 + 结果快照 + objectKey，历史报告读快照不重跑，重试接口用状态机守卫防 SUCCESS 被覆盖

第二轮做”资源统一治理”：散落的 MinIO 上传逻辑收敛为 MediaService 单一入口，五道安全校验纵深防御，objectKey 入库 + URL 动态生成的存用分离设计，老接口门面保兼容，异常观察图片附件全链路接入
